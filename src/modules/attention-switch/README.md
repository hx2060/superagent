# attention-switch · 多种类任务切换注意力（占位 · 设计中）

> **状态：占位 / 设计讨论阶段。未实现、未接入主干。**
> 需求方原话：「先占位不执行……目前只有一个雏形想法……需要先占点讨论在执行设计」；后续要求「沿着 PR #8 先按照模块分离的形式，进行对应项目查询探讨，给出几种可能的执行方案」。
> 本文档是设计讨论的载体；「开放问题」有方向之前，不写实现、不改主干。

## 1. 需求理解

### 1.1 原始诉求

> 「存在很多需要做的内容，但是在某些时刻一点工作都不想做，导致逃避情况。我认为关键在于没有多种类工作进行注意力的转换。」

### 1.2 拆解

| 要素 | 理解 | 待确认 |
| --- | --- | --- |
| 触发场景 | 任务总量大；某些时刻启动阻力极大，完全不想开始 | 「某些时刻」是否有规律（如午后、疲劳时） |
| 需求方假设 | 一类工作引发阻力时，切换到另一类工作可降低启动成本 | 假设本身待小步验证 |
| 真实目标 | 不是「做得更多」，而是「卡住时仍能启动」，维持推进感 | 是否需要度量「推进感」 |
| 核心机制 | 「多种类工作」+「注意力转换」 | 种类维度与转换触发方式（见第 6 节） |

一个关键区分：**「逃避」目前只有需求方本人能感知**。系统能拿到的是任务状态与时间，拿不到「此刻不想动」。因此自动检测只能是代理信号（如某类任务长时间无状态变化）；更稳妥的形态是提供低成本的「我卡住了」手动入口。这一点直接影响方案选型，需要需求方表态（开放问题 2）。

## 2. 项目现状查询（模块分离形式下的积木）

以下为对当前仓库的实际查询结果（`main` 基线，即 PR #8 的基线）：

**已落地模块与注册点**（`src/app.js` 中每个模块 = 1 处 import + 1 个槽位 + 1 处 mount / destroy + `index.html` 中 1 行样式 link）：

| 模块 | 槽位 | 共享服务 | 数据快照 |
| --- | --- | --- | --- |
| `daily-tasks` | 日视图 `<div data-module-root="daily-tasks">` | `services.dailyTasks` | `data.dailyTasks` |
| `inbox` | 日视图 `<aside class="day-sidebar" data-module-root="inbox">` | `services.inbox` | `data.notes` / `data.tasks` |
| `week-chart` | 周视图 `<div class="mod-week-chart-root" data-module-root="week-chart">` | `services.inbox` | `data.events` / `data.tasks` |

**可用的数据与服务**：

- `Task`：`{ id, title, icon, status, date?, start?, duration?, end?, due? }`；未排期为 Inbox，填写时间后同步日 / 周 / 月。
- `DailyTask`：`{ id, title, icon?, recurrence: 'daily' }`；状态按日隔离。
- `services.inbox` / `services.dailyTasks`：增改删、三态循环、订阅。
- `window.schedule`：dsh 运行时输入接口（`docs/schedule-api.md`）。

**扩展点规则**（`AGENTS.md` 第 2 节、`docs/interfaces.md` 5.1）：新模块放 `src/modules/<name>/`，遵守 `mount(context)` 契约；样式 `.mod-<name>-` 前缀；新 service 键必须可选、先提案；主干注册改动需评审。

**持久化边界**：编辑只存当前页面会话；具体内容写 `local/schedule.json`（不提交）；仓库只交机制层。

**结论**：「注意力切换」可以完全按模块分离落地。需要的主干改动上限是：一个视图槽位 + 一个可选 service 键 + 一行样式 `<link>`；不动月 / 周 / 日既有视图逻辑。数据侧是否引入字段见方案一的设计说明。

## 3. 候选执行方案

以下均为提案，未选定，按「从小到大」排列；方案之间可组合。

### 方案一：种类标签 + 分组 / 筛选（数据先行）

- **形式**：给任务增加「工作种类」标签；`attention-switch` 模块在日视图提供按种类分组 / 筛选的面板，只读 `services.inbox` / `services.dailyTasks`。
- **需求映射**：切换的前提是「知道自己有哪些种类的工作」；先把「多种类」变成可见、可管理的数据。
- **模块与接入点**：`src/modules/attention-switch/{index.js, README.md, styles.css, __tests__/}`；主干新增日视图槽位一行 + 样式 link 一行；**不需要新 service**。
- **种类分配的两种存放方式**（实现时二选一，需在接口提案中定）：
  - a. 模块内会话映射（`taskId → kind`，刷新即忘）：主干与数据契约零改动，最小；
  - b. 数据字段 `Task.kind?` / `DailyTask.kind?`（可选、增量）：可经 `local/schedule.json` 与 dsh 下发持久，需要同步 `docs/interfaces.md` 与 `docs/schedule-api.md`。
- **验证**：种类校验 / 分组纯逻辑 node:test；UI 按 1440 / 1024 / 768 / 390 本地验证，证据留 `local/evidence/`。
- **优点**：最小可用、可回退；为后续方案打底；产品风险低。
- **代价**：种类分配需要入口（模块内表单或 dsh 下发）；单独看没有「切换」的主动辅助。

### 方案二：「换一类」切换助手（独立模块面板）

- **形式**：日视图模块面板，展示各类任务数量与今日完成情况；提供「我卡住了 → 换一类」入口：点击后推荐另一类并列出该类任务，可把某任务推为「下一步」。当前所在类与切换历史只存会话。
- **需求映射**：直接实现「注意力的转换」机制。
- **模块与接入点**：方案一全部 + 提案最小 `services.attentionSwitch`（记录当前类与切换事件；会话内、不落盘；键可选，旧模块不受影响）。
- **数据 / 接口变更**：种类分配同方案一；切换记录为会话态，不写入已发布数据契约。
- **验证**：推荐规则纯逻辑单测；UI 本地验证。
- **优点**：机制直白、模块自包含；不碰清单 / 周图 / 月视图。
- **代价**：「推荐哪一类」需要规则（轮换 / 今日完成最少 / 需求方指定优先级）——规则本身是产品决策（开放问题 3）。

### 方案三：切换助手 + 逃避记录与回顾

- **形式**：方案二 + 记录「逃避 / 切换」事件（时刻、从哪类到哪类、随后是否完成）；在日视图或周视图提供简单回顾：哪类工作最容易卡、切换后是否更容易启动。
- **需求映射**：用本地数据回答「我到底在哪种工作上逃避」，让需求方假设可被验证。
- **模块与接入点**：方案二全部 + 周视图一个只读展示位（可选，需评审）。
- **数据 / 接口变更**：本地事件记录（`local/`，不提交）；无新发布字段。
- **验证**：事件聚合纯逻辑单测；UI 本地验证。
- **优点**：形成「假设 → 记录 → 验证」闭环；数据只在本地。
- **代价**：记录字段与回顾形式是新产品决策；工作量最大；需明确隐私边界（仅本地会话 / 本地文件，不上传）。

### 方案四（对照，不建议）：改造现有清单模块

- **形式**：不新增模块，直接在 `inbox` 清单里加「种类」列与筛选 chips，`daily-tasks` 条同样支持种类。
- **优点**：零新注册点。
- **代价**：修改既有模块职责，违背需求方「按照模块分离的形式」的要求；清单 UI 变重；与 `AGENTS.md` 模块化方向不一致。
- **列出目的**：仅作对照，帮助确认「新模块」的边界。

## 4. 方案对比

| 维度 | 方案一 种类标签 | 方案二 切换助手 | 方案三 助手+记录 | 方案四 改清单 |
| --- | --- | --- | --- | --- |
| 对「逃避」的直接缓解 | 间接（可见性） | 直接 | 直接 + 事后洞察 | 间接 |
| 主干改动 | 槽位 + 样式各一行 | 同左 + 可选 service 键 | 同左 + 周视图只读位 | 改既有模块 |
| 数据契约变更 | `kind?`（可选）或会话映射 | 同左 + 会话态 | 同左 + 本地记录 | `kind?`（可选） |
| 新产品决策量 | 种类枚举 | + 推荐规则 | + 记录与回顾形式 | 最少 |
| 可回退性 | 高 | 高 | 中 | 低 |
| 相对工作量 | 1 | 2 | 3 | 1.5 |

## 5. 建议的探讨路径（建议，非决定）

小步迭代，每步可独立交付与回退：

1. **第一迭代 · 方案一**：把「多种类」变成数据与可见面板，验证种类划分是否好用。
2. **第二迭代 · 方案二**：在种类之上加「换一类」入口，验证切换是否降低启动阻力。
3. **第三迭代 · 方案三**：加本地记录与回顾，用数据检验「哪种工作最容易逃避」。

## 6. 开放问题（需要需求方决策）

1. **种类维度与枚举**：「多种类工作」按什么划分？候选维度：认知负荷（深度 / 浅层）、动作类型（创作 / 整理 / 沟通 / 学习）、场景（电脑前 / 线下 / 外出）。请给出你的划分与每类的例子。
2. **触发方式**：「我卡住了」用手动入口即可，还是希望按规则自动提示（如某类任务长时间无状态变化）？
3. **推荐规则**：「换一类」换到哪一类——随机 / 今日完成最少 / 你指定优先级？
4. **切换粒度**：切到「另一类的任务」，还是切到「一个两分钟起步动作」（如「只打开文档」）？
5. **是否记录**：是否记录逃避 / 切换事件（只存本地）用于回顾？
6. **第一迭代范围**：是否按「方案一 → 方案二」的小步路径走？第一迭代做到哪一步？

## 7. 边界与约束（不随方案改变）

- 主干冻结：注册点、service、样式入口等接入改动需需求方确认并评审（`AGENTS.md` 第 1、2 节）。
- 数据契约只做增量：新增字段必须可选；不重命名 / 删除已发布字段。
- 零运行时依赖、无构建步骤；样式必须 `.mod-attention-switch-` 前缀。
- 机制层 / 内容分离：记录与内容只留本地；仓库与 PR 不出现真实日程、截图或飞书私有内容。
- 不猜测产品方向：种类划分、触发与推荐规则归需求方。
