# attention-switch · 多种类任务切换注意力（占位 · 设计中）

## 1. 问题背景（来自需求方）

- 待做内容很多，但某些时刻**一点工作都不想做**，形成逃避。
- 需求方假设：关键在于**没有多种类工作进行注意力的转换**——当一类工作引发阻力时，换一类工作可以降低启动成本，让注意力有落点，保持推进感。

这不是日历缺陷，而是一个待验证的产品假设；模块的第一步是把这个假设变成可讨论、可小步验证的设计。

## 2. 模块概念（雏形）

在**现有任务集合**（清单 `Task`、每日任务 `DailyTask`）之上增加「工作种类」维度，并在逃避 / 卡住时刻提供**换一类**的入口：

- 分类：把任务归入少数几种工作类型（具体种类待需求方定义，见开放问题 1）。
- 切换：卡住时从当前类切换到另一类，降低「开始」的心理成本。
- 反馈：可选地记录切换与逃避发生的情况，帮助识别哪类工作最容易逃避。

模块定位是现有数据上的**辅助层**：不新建第二套任务系统，不修改已发布接口。

## 3. 候选形态（待讨论，未选定）

| # | 形态 | 一句话描述 | 主要代价 |
| --- | --- | --- | --- |
| A | 种类标签 + 分组 / 筛选 | 给任务加可选 `kind`，清单与视图按类分组或筛选 | 需要需求方定义种类；改动清单 UI |
| B | 「换一类」切换助手 | 日视图一个模块：显示当前类与可选类，一键列出另一类的任务 | 需要注册点与可能的推荐逻辑 |
| C | 轻度起步动作 | 每类配一个「小到不可能失败」的起步动作（如「只打开文件」） | 需要维护每类的起步文案 |
| D | 逃避 / 阻力记录 | 记录「不想做」发生的时刻与种类，按类统计 | 引入新数据与隐私边界，需需求方确认 |

形态之间不互斥：例如 A 是基础，B 是入口，C / D 是可选增强。**建议从 A + B 的最小组合开始讨论。**

## 4. 接口提案（草案，未定）

以下均为**提案**，实现前需按 `AGENTS.md` 第 2 节提交最小接口提案并评审：

- **数据（增量）**：`Task` / `DailyTask` 增加可选 `kind?: string`；种类枚举固定为一小组（取值待开放问题 1）。新字段可选，旧数据不受影响。
- **服务（只读优先）**：模块只读 `services.inbox` / `services.dailyTasks`；若需要记录「种类分配」或「切换历史」，再提案最小 store（如 `services.attentionSwitch`），不直接 `import` `src/app.js`。
- **注册点**：候选为日视图槽位（类似 `daily-tasks` / `inbox`）或独立视图；未定，见开放问题 3。
- **持久化**：与现有模块一致，页面会话内有效；具体内容只写 `local/schedule.json`，不提交仓库。

## 5. 不变量与约束

- 主干冻结：注册点、`services`、样式入口等接入改动需需求方确认并评审（`AGENTS.md` 第 1、2 节）。
- 数据契约只做增量：新增字段必须可选，不得重命名 / 删除已发布字段。
- 零运行时依赖、无构建步骤；样式必须 `.mod-attention-switch-` 前缀。
- 不记录敏感内容；仓库与 PR 不出现真实日程、截图或飞书私有内容。
- 不猜测设计方向：种类划分、触发方式等产品决策归需求方。

## 6. 开放问题（需要需求方决策）

1. **种类清单**：你心中的「多种类工作」具体是哪几类？每类的定义与例子是什么？（例如：深度专注 / 轻度事务 / 创意发散 / 机械整理 / 沟通协作——仅示例，以你的说法为准。）
2. **触发方式**：手动点「换一类」就够，还是希望某种自动建议（如检测到长时间未推进）？
3. **落地形态**：独立模块面板、扩展现有清单，还是新的视图？
4. **切换粒度**：切到「另一类任务」，还是切到一类中的「小步起步动作」（形态 C）？
5. **是否需要记录**：是否记录逃避 / 切换发生的时间与种类（只存本地会话），用于事后回看？
